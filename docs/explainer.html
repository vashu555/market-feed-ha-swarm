Market HA Swarm

A live price dashboard that keeps working when parts of it break. It runs on two Oracle Cloud servers in different cities, managed as one Docker Swarm cluster, with a home PC acting as tie-breaker.

The idea

Two branches of the same shop

Think of a shop with two branches, one in Mumbai and one in Hyderabad. Each branch has a front desk (the load balancer) and two counters (the APIs). A customer can walk into either branch, and the front desk sends them to whichever counter is free, even one in the other city.

Behind the counters is one notice board (Redis) where a clerk (the generator) pins a new price every quarter second. Every counter reads the board and calls the new price out to its customers.

A committee of three managers decides who works where: the two branches, plus a third member who works from home (your PC). If a branch burns down, the other two members vote and move the notice board and clerk to the surviving branch.

Big picture

Where every piece runs and what it talks to

Each VM serves users on its own public address. Behind that, all four APIs and the single Redis work as one pool across both cities, connected through an encrypted private network (NetBird). What if it breaks reuses this picture to show what each failure takes out.

Four layers

Each layer depends on the one below

1 · MachinesOracle Cloud + home

Two Ubuntu servers (ARM) in different Oracle regions, plus a home PC. Each VM has its own public IP. There is no shared local network between them.

2 · Private networkNetBird / WireGuard

NetBird gives all three machines private 100.93.x.x addresses that can reach each other over an encrypted tunnel, even across cities and home NAT. All cluster traffic goes over this, never the open internet.

3 · Cluster controlDocker Swarm

The three machines form one Swarm with three managers. The managers agree by majority vote on what runs where, and restart or move containers when something dies.

4 · The appcontainers

Seven containers: 2 HAProxy, 4 APIs, 1 Redis, 1 generator. They are connected by two virtual networks that span both VMs: frontend_net (load balancers ↔ APIs) and data_net (APIs ↔ Redis ↔ generator, no internet access).

Request & tick flow

Following one visitor and one price

A visitor opens the dashboard

  1. The browser opens http://<Hyderabad public IP>:18080/.
  2. Hyderabad's HAProxy picks the next API in rotation, which might be api-1 on Mumbai. The request then crosses the NetBird tunnel.
  3. The API returns the dashboard page (one HTML file with built-in JavaScript).
  4. The page opens a WebSocket to /ws/market. HAProxy routes it the same way, and the connection stays open.
  5. Every 2.5 s the page also calls /whoami to show which load balancer and API served it.

A price travels to the screen

  1. The generator (Hyderabad) moves a price by a small random step and builds a JSON message with a sequence number.
  2. It publishes the message to the Redis channel market.ticks on Mumbai.
  3. Redis instantly forwards it to every subscriber: all four APIs.
  4. Each API copies the tick into a small queue for each browser connected to it.
  5. The tick goes down the WebSocket, and the page updates the table and chart. Redis keeps no history, so a tick missed during a reconnect is gone.
Voting

Why the home PC is part of the cluster

Swarm only changes things (start, stop, move a container) when more than half of the managers agree. With three managers, that means any two.

3 of 3

All online. Swarm works.

2 of 3

One machine lost. Swarm still works and repairs things.

1 of 3

Swarm freezes. Running containers keep running, but nothing is moved.

The rule exists to prevent split brain. If the link between Mumbai and Hyderabad broke, each VM would see the other as dead. Without a vote, both would start their own Redis and generator, and users would get two different sets of prices. With three voters, only the side that can still reach a second machine has a majority, and the lone side does nothing.

With only the two VMs, losing either one would leave the survivor with 1 of 2 votes, which is not a majority, so nothing could recover. The PC is the third vote that makes "any two" possible. It never runs the app itself: it is drained, so the containers always run on a VM. Any manager, the PC included, can be elected Leader and decide where things go.

The code

How each piece is written

There are four small programs (generator, API, dashboard, load balancer config) and one file that tells Swarm how to run them all.

Generator

generator/main.py · Python

An endless loop that makes up prices. Each price takes a tiny random step (a "random walk"), so the chart looks like a real market. It never stores anything.

prices[symbol] = max(1, prices[symbol] + rng.gauss(0, reference * 0.00008))
tick = {"type": "tick", "simulated": True, "sequence": sequence,
        "symbol": symbol, "price": price, "bid": ..., "ask": ...}
await conn.publish(CHANNEL, json.dumps(tick))   # to Redis channel market.ticks
await asyncio.sleep(INTERVAL)                   # 0.25 s

It cycles through NIFTY, BANKNIFTY and RELIANCE. If Redis is unreachable it waits one second and retries.

Redis

redis:7.4-alpine · no custom code

A message hub used in publish/subscribe mode: whatever the generator publishes, every subscribed API receives at once.

redis-server --save "" --appendonly no   # keep nothing on disk

Persistence is switched off on purpose. Ticks are live-only, so Redis can be restarted on any VM without needing to copy data.

API (×4)

api/app.py · Python, FastAPI

The web server. Each copy is identical and has no state worth saving, which is why there can be four of them and any of them can answer.

# Background task: listen to Redis and copy every tick to each browser's queue
await pubsub.subscribe(CHANNEL)
for queue in tuple(CLIENTS):            # one queue per open WebSocket
    if queue.full(): queue.get_nowait()   # slow browser? drop its oldest tick
    queue.put_nowait(payload)

# Health check used by HAProxy: healthy only if Redis answers within 1.5 s
@app.get("/health")
async def health():
    if await asyncio.wait_for(redis_client.ping(), timeout=1.5):
        return {"ok": True, "instance": INSTANCE_NAME, "region": REGION}
    return JSONResponse({"ok": False, ...}, status_code=503)

# The live feed
@app.websocket("/ws/market")
async def market_websocket(websocket):
    await websocket.accept()
    await websocket.send_json({"type": "hello", "api": INSTANCE_NAME, "region": REGION})
    while True:
        await websocket.send_text(await queue.get())
  • / serves the dashboard page.
  • /whoami says which API and VM answered. It doesn't touch Redis, so it's also used as the "is the process alive" check.
  • /health says "I can do real work". The 1.5 s limit makes it fail fast when Redis dies; without it, the check hung and failover took about 15 s instead of about 9–12 s.
  • Each browser's queue holds at most 100 ticks, so one slow viewer can't hold up the others.

Dashboard

api/static/index.html · HTML + JavaScript

The page in the browser. It heals itself: if the connection drops, it reconnects to the same address, and the load balancer sends it to a healthy API.

ws = new WebSocket('ws://' + location.host + '/ws/market');
ws.onclose = () => setTimeout(connect, 2000);          // reconnect after 2 s
setInterval(() => {                                      // connection open but silent?
  if (Date.now() - lastTickAt > 5000) ws.close();      // force a reconnect after 5 s
}, 1000);

It shows the load balancer from the X-LB-Node response header, and the API and VM from the WebSocket's first "hello" message.

Load balancer

swarm/haproxy-swarm.cfg · HAProxy 3.2

Receives every visitor and passes them to a healthy API. It finds the APIs by asking Docker's built-in DNS, so it notices automatically when Swarm moves one.

resolvers docker
    nameserver docker_dns 127.0.0.11:53          # Docker's built-in DNS

backend api_pool
    balance roundrobin                           # take turns
    option httpchk
    http-check send meth GET uri /health ...      # ask each API "can you work?"
    default-server inter 2s fall 3 rise 2 check resolvers docker init-addr none
    server-template api 6 tasks.market_api:8000  # 6 slots filled from DNS

frontend market_front
    bind :8080
    http-request return status 200 ... if lb_health { nbsrv(api_pool) gt 0 }
    http-response set-header X-LB-Node "${NODE_NAME}"

defaults
    timeout tunnel 1h                            # keep WebSockets open
  • tasks.market_api returns the address of every running API on either VM.
  • inter 2s fall 3 rise 2: check every 2 s, mark an API dead after 3 failures (about 6 s), and alive again after 2 successes.
  • /lb-health answers 200 only if at least one API is usable. A future health-checked DNS name or tunnel would use it.

Swarm stack

swarm/stack.yaml · Docker Compose format

The instructions Swarm follows: which containers, how many, where they may run, which networks, and how to update them.

api:
  image: market-api:1.0
  environment:
    INSTANCE_NAME: "api-{{.Task.Slot}}"      # api-1 … api-4
    REGION: "{{.Node.Hostname}}"             # which VM it landed on
  deploy:
    replicas: 4
    placement: {max_replicas_per_node: 2}   # exactly 2 per VM
    update_config: {parallelism: 1, delay: 5s, order: stop-first}

haproxy:
  deploy: {mode: global}                     # one per active machine
  ports:
    - {target: 8080, published: 18080, mode: host}

redis:     {deploy: {replicas: 1}}           # no placement rule: free to move
generator: {deploy: {replicas: 1}}

networks:
  frontend_net: {driver: overlay, driver_opts: {com.docker.network.driver.mtu: "1230"}}
  data_net:     {driver: overlay, internal: true, ...}

Deployed from any manager with docker stack deploy -c stack.yaml --resolve-image never market. The stack name must be market, because HAProxy looks up tasks.market_api.

Cluster setup

one-time commands

How the three machines were joined into one Swarm, using only their NetBird addresses.

# Mumbai: create the cluster
docker swarm init --advertise-addr 100.93.145.73 --listen-addr 100.93.145.73:2377 \
  --data-path-addr 100.93.145.73 --default-addr-pool 10.200.0.0/16

# Hyderabad and the PC: join as managers (each with its own NetBird IP)
docker swarm join --token <manager token> --advertise-addr <own IP> \
  --listen-addr <own IP>:2377 --data-path-addr <own IP> 100.93.145.73:2377

# Keep the PC as a voter only, and label the VMs
docker node update --availability drain home-pc
docker node update --label-add region=mumbai instance-20260319-0225
docker node update --label-add region=hyderabad oci-hyderabad
Design decisions

Why it is built this way

No Keepalived floating IP
A floating IP can only move between machines on the same local network. Mumbai and Hyderabad are different Oracle regions, and Oracle also ignores the network announcements Keepalived relies on. Each VM keeps its own address instead; one shared address is planned through Cloudflare Tunnel.
Three managers, home PC as the third
A Swarm with two managers cannot survive losing one, because 1 of 2 is not a majority. India has only these two Oracle regions, so the tie-breaker has to live somewhere else. The PC is a free stand-in; a small always-on server elsewhere would be the permanent fix.
PC is drained
Otherwise Swarm could place Redis or a load balancer on a home PC that sleeps, sits behind home internet, and is x86 while the app images are built for ARM.
NetBird private network
Swarm needs the machines to reach each other on a fixed address. NetBird provides that over WireGuard encryption, so the Swarm ports never face the internet.
Swarm uses 10.200.0.0/16
Swarm's default internal range starts at 10.0.0.0, the same range as the VMs' own Oracle network (10.0.0.x). The clash would have broken networking on the VMs, including the website.
Network MTU 1230
NetBird packets carry 1280 bytes and Swarm's overlay adds 50 bytes of wrapping. Without the lower limit, small requests work but large WebSocket messages stall, which is very hard to diagnose.
Port 18080, host mode
Ports 80 and 443 belong to the website's nginx on Mumbai. Host mode means each VM's own HAProxy answers on that VM, instead of Swarm forwarding traffic between machines.
Exactly 2 APIs per VM
Swarm's "spread evenly" preference placed them 3 + 1 in practice. A hard limit of 2 per VM matches the plan of one load balancer plus two APIs per VM.
Updates replace one API at a time, stop-first
With the 2-per-VM limit there is no room to start a new copy before stopping the old one; a start-first update hung forever. Three APIs keep serving while the fourth is replaced.
Two different health checks
Swarm checks /whoami ("is the process alive"), and HAProxy checks /health ("can it reach Redis"). If Swarm used /health, it would kill all four APIs whenever Redis was being moved.
Redis and generator not pinned
They have no placement rule, so Swarm can restart them on whichever VM survives. That is the main thing the third vote buys.
Images built on each VM, no registry
Both VMs are ARM, so each builds market-api:1.0 and market-generator:1.0 locally, and the deploy uses --resolve-image never. That avoids publishing images anywhere.
Only port 18080 is public
The Oracle firewall opens only the app port. HAProxy stats (18404) and the Swarm ports (2377, 7946, 4789) are closed to the internet; this was checked after opening the port.
Hyderabad hostname pinned
Renaming an Oracle instance in the console doesn't rename the server, and cloud-init resets the hostname at every boot. A cloud-init setting now keeps oci-hyderabad after a reboot.

Glossary

Words used on this page

Container
A packaged program with everything it needs, running isolated on a machine.
Image
The template a container starts from, like market-api:1.0.
Docker Compose
Runs several containers together on one machine from one file.
Docker Swarm
Runs containers across several machines as if they were one, and repairs them when something fails.
Node
One machine in the Swarm.
Manager / Leader
Managers hold the cluster's records and vote. The Leader is the manager currently making decisions.
Drain
A node setting meaning "run no containers here". The node still votes.
Service / replica / task
A service is "run 4 copies of the API". Each copy is a replica, and Swarm tracks each one as a task.
Overlay network
A virtual network that spans several machines, so containers on different VMs can talk as if side by side.
Load balancer (HAProxy)
Receives every visitor and passes them to one of several servers, skipping unhealthy ones.
Health check
A regular "are you OK?" request. Fail it a few times and you stop getting traffic.
WebSocket
A connection that stays open, so the server can push new prices without the browser asking each time.
Publish / subscribe
One sender posts a message to a channel, and every listener on that channel receives it.
VPN (NetBird)
An encrypted private network laid over the internet. NetBird is built on WireGuard.
Floating IP (Keepalived)
One address that jumps to a backup machine on the same local network when the main one fails.
Quorum / split brain
Quorum is the majority needed to decide. Split brain is two halves each acting as if they were in charge.
Commands

Everyday commands

Run these on any manager: Mumbai, Hyderabad, or the PC's WSL. Add sudo on the VMs.

docker node ls                       # are all 3 machines healthy? who is Leader?
docker service ls                    # how many copies of each service are running
docker service ps market_api         # which VM each API is on
docker service logs -f market_api    # live logs from all 4 APIs

# Deploy a change (on a VM, from ~/market-ha/swarm)
docker stack deploy -c stack.yaml --resolve-image never market

# Rebalance APIs after a VM comes back
docker service update --force market_api

# Quick check from anywhere
curl http://<VM public IP>:18080/lb-health    # "ok" = this load balancer has a working API
curl http://<VM public IP>:18080/whoami       # which API and VM answered
